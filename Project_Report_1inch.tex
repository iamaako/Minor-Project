\frontchapter{Abstract}
Programming examinations are conducted in computer laboratories, yet the tools that are normally available either run inside an ordinary browser that a candidate can leave at any moment, or depend on an internet connection and on cloud services. This project presents \ProjectTitle, a desktop examination system for a local network. It consists of two applications. The Student Portal runs on every candidate's computer in a locked full-screen mode, presents the questions, lets the candidate write, compile and run programs in Python, C and C++, and submits the work. The Admin Server runs on the invigilator's computer, stores students, questions and submissions in a SQLite database, controls the examination, and shows live activity in a web dashboard.

The system combines several controls that are normally found only in separate products: licence binding to a machine, binding of a roll number to one computer, blocking of system shortcuts and removable drives, a locally executed code runner with bundled compilers, analysis of the candidate's typing behaviour, and an on-device camera proctor. The proctor uses the MediaPipe Face Landmarker to estimate head direction and iris position, calibrates itself for every candidate, and reports looking aside, looking down, absence of the face and a covered or disconnected camera to the invigilator together with a snapshot. No video leaves the candidate's computer.

The system was tested with automated checks of the server and the code runner and with a simulated camera. The face landmark model needed about 19 ms per frame on the development laptop. The student installer is 191 MB and the admin installer is 86 MB, including the compilers.

\vspace{0.4cm}
\noindent\textbf{Keywords:} online examination, kiosk mode, code execution, face landmarks, gaze estimation, Electron, Socket.IO.

\section{Background}
Practical examinations in programming courses require the candidate to write a program, compile it and observe its output. Paper-based examinations cannot test this, and unsupervised computer-based tests make it easy to look up answers, to copy code from a neighbour, to bring prepared code on a pen drive, or to ask another person for help. In a university laboratory the invigilator can see the room, but cannot see what is on thirty screens at the same time.

A computer-based examination for programming therefore has to do three things together. It has to restrict what the candidate's computer can do during the examination, it has to give the candidate a working programming environment, and it has to give the invigilator a live view of what every candidate is doing. This project builds such a system for the computer laboratories of the Interdisciplinary Centre for Artificial Intelligence.

\section{Problem Statement}
General-purpose quiz and coding platforms run in a web browser, need a stable internet connection and cannot stop the candidate from switching to another window. Browser lockdown tools restrict the computer but do not provide a place to compile and run programs, and cloud proctoring services upload the candidate's video to a remote server. A laboratory needs a single system that works on its own network, locks the computer, runs the candidate's code locally and monitors the candidate without sending video elsewhere.

\section{Objectives}
The objectives of the project are:
\begin{enumerate}
  \item to build a student application that locks the computer in full-screen mode for the duration of the examination;
  \item to provide in the same application an environment where Python, C and C++ programs can be written, compiled and run without any software installed on the computer beforehand;
  \item to build an admin application that manages students and questions, controls the examination and shows live activity;
  \item to detect looking aside, looking down, absence of the candidate and tampering with the camera, using only on-device processing;
  \item to bind the software to authorised machines and every candidate to one computer; and
  \item to package both applications as installers that can be deployed on laboratory machines.
\end{enumerate}

\section{Organisation of the Report}
Chapter~2 reviews related work. Chapter~3 states the requirements and the technologies chosen. Chapter~4 describes the design with the architecture, data flow diagrams, the database design and flowcharts. Chapter~5 explains the implementation of each module. Chapter~6 lists the test cases and the measurements. Chapter~7 concludes the report and suggests future work. Screenshots of both applications are collected in Appendix~A.

\chapter{Literature Review}
%% ----------------------------------------------------------------------

\section{Online Examination and Code Judging Platforms}
Online judges and coding-assessment platforms such as HackerRank and CodeChef evaluate programs on a remote server and are designed for large numbers of remote candidates. They need an internet connection and run in a browser, so the candidate's computer is not restricted. Learning-management systems such as Moodle offer quizzes and, through plug-ins, programming exercises that are evaluated on the server, but again the examination runs inside a normal browser.

\section{Lockdown Browsers and Kiosk Applications}
Safe Exam Browser~\cite{seb} is a widely used application that opens an examination web page in a locked browser window, blocks other applications and disables shortcuts. It protects web-based quizzes. It does not provide a compiler, so a candidate cannot compile and run a program inside it. Building a locked application with a desktop framework such as Electron~\cite{electron} makes it possible to combine the lock with a local code runner, because the application has access to the operating system through a controlled bridge.

\section{Automated Proctoring using Face Analysis}
Camera-based proctoring estimates whether the candidate is looking at the screen. The two common signals are the direction of the head and the direction of the eyes. MediaPipe~\cite{mediapipe} provides a framework for running such perception models on the device, and its face mesh model estimates 468 three-dimensional landmarks of the face in real time on ordinary hardware~\cite{kartynnik}. The Face Landmarker task~\cite{landmarker} extends the model with ten iris landmarks and with blendshape scores that describe, for example, the eyelids and the direction of the eyes. These outputs are enough to compute head yaw and pitch and an iris position inside the eye, which is the basis of the proctor in this project.

\section{Comparison and Research Gap}
Table~\ref{tab:compare} compares the approaches that were studied with the system developed here.

\section{System Architecture}
The system follows a client--server design on a single local network, as shown in Figure~\ref{fig:arch}. The Admin Server is the only authority. It holds the database, decides which student may log in and which questions the student receives, and relays commands to students. Every Student Portal connects to it through a WebSocket connection on one TCP port. The dashboard is an ordinary web page served by the same server, so the invigilator can also supervise from a laptop or a phone.

The Student Portal is built from three layers (Figure~\ref{fig:modules}). The renderer displays the pages and runs the camera analysis, but it is sandboxed and cannot touch the operating system. The main process performs everything that needs privileges, such as the locked window, the keyboard lock, compiling and running programs, and the network connection. A small preload bridge exposes only a fixed list of functions from the main process to the renderer.

\section{Licensing and Device Binding}
The portal refuses to start the examination on a computer that has not been authorised. The administrator creates a licence token file with the Admin Server and copies it to a USB drive. When the drive is inserted the portal finds the token, decrypts it with AES-256-CBC and, if it is valid, writes a machine lock file. The lock stores the hardware identifier of the computer, which is read from the system, encrypted with AES-256-CBC, and is checked at every start. Copying the installed program to another computer therefore does not work.

A second binding is made at the server. The first time a student logs in, the address of the computer is stored with the roll number. A login from another address is rejected until the administrator removes the binding, which is needed when a computer fails and the student has to move to another one.

\section{Examination Lockdown}
The main window is created in full-screen kiosk mode, always on top and without a frame. The renderer runs with context isolation and the Chromium sandbox switched on and with Node.js disabled, and the page carries a content security policy that allows nothing from the network. The only permission granted to the page is the camera.

Shortcuts such as Alt+Tab, Alt+F4, the Windows key, the function keys and the developer tool shortcuts are registered and swallowed by the application. A small helper program installs a low-level keyboard hook for the keys that Windows does not hand to an application. Whenever the window loses focus, it is brought back and the event is counted and sent to the server. A second helper listens to the Windows management events for a new removable drive. If a drive is inserted during the examination the server locks that student and shows an alarm on the dashboard. The invigilator can leave the locked application with a secret key combination.

\section{Code Execution Module}
Every student has a workspace folder named after the roll number. The program that is open in the editor is written to a file in this folder, so helper files and several source files can be used together. For C and C++ the file is compiled with the bundled GCC 16.1.0 using static linking, and the result is started as a separate process. Python programs are started with the embedded interpreter in unbuffered mode, so that output appears while the program is still running. The standard input of the process is connected to the terminal of the portal, which makes interactive programs possible.

A process is stopped after 120 seconds or after 300 KB of output. Before a program is started, its text is scanned for calls that give access to the operating system, for example the \texttt{os} and \texttt{subprocess} modules in Python and \texttt{system()} in C. File names that arrive from the page are checked against a strict pattern so that a name cannot point outside the workspace. The scan is a first barrier and not a complete sandbox. It is mentioned again among the limitations in Chapter~6.

\section{AI Proctoring Module}

\subsection{Frame Capture and Landmark Detection}
The camera is opened at 640$\times$480 and about ten frames per second are analysed. The MediaPipe Face Landmarker returns 478 landmarks for the face, of which ten belong to the irises, and a set of blendshape scores. The model file and the WebAssembly runtime are part of the installer, so nothing is downloaded. The detector uses the graphics processor when it is available and the processor otherwise.

\subsection{Head Direction and Eye Direction}
The head yaw $\psi$ is estimated from the position of the nose tip $x_n$ between the two edges of the face $x_L$ and $x_R$. Because the nose projects about half a face width in front of the face contour, the offset of the nose is $0.5\tan\psi$, which gives
\begin{equation}
\psi = \arctan\!\left(\frac{2\,\bigl(x_n-\tfrac{x_L+x_R}{2}\bigr)}{x_R-x_L}\right).
\end{equation}
For each eye the position of the iris centre $x_i$ between the outer corner $x_o$ and the inner corner $x_c$ of the eye is
\begin{equation}
r = \frac{x_i-x_o}{x_c-x_o},
\end{equation}
and $\bar r$ is the mean of both eyes. The pitch ratio $\rho$ compares the vertical position of the nose tip $y_n$ with the brow $y_b$ and the chin $y_c$:
\begin{equation}
\rho = \frac{y_n-y_b}{y_c-y_b}.
\end{equation}
A student who looks at the screen has some values $\psi_0$, $\bar r_0$ and $\rho_0$ that depend on the seat and on the position of the camera. The direction of gaze is therefore measured relative to these values:
\begin{equation}
\theta = (\psi-\psi_0) + 150\,(\bar r-\bar r_0).
\end{equation}
The factor 150 converts the shift of the iris inside the eye into degrees and was chosen from the geometry of the eyeball. The student is treated as looking aside when $|\theta|$ exceeds $30^\circ$. Looking down is detected when $\rho-\rho_0$ exceeds 0.10 or when the blendshape for eyes looking down rises by more than 0.35 above its calibrated value. All angles are signed so that left and right refer to the student's own left and right.

\subsection{Calibration and Violation Rules}
When the examination starts, the portal asks the student to look at the screen for about two seconds. The median of 15 suitable frames gives $\psi_0$, $\bar r_0$ and $\rho_0$. Frames in which the head is already turned or the eyes are closed are ignored. If the student does not look at the screen, neutral values are used.

Values of a single frame are noisy, so they are smoothed and a violation needs a condition to hold for some time. The rules are given in Table~\ref{tab:rules}. A short return to the centre of less than 0.7 s, as with a blink, does not reset the timer, and changing from left to right keeps the same episode, so that quickly turning from one side to the other does not hide the violation.

\midrule
LOOKING\_BESIDE & $|\theta|>30^\circ$ to the left or right, by head, by eyes or by both & 2 s\\
LOOKING\_DOWN & Head or eyes pointing down & 8 s\\

When a violation is recorded, a snapshot of 320$\times$240 pixels is taken from the video and sent with the type, direction and duration. The student sees a warning banner and a counter in the status bar. The same violation type is not reported again for 4.5 s, and absence is not reported again for 15 s, to keep the dashboard readable.

\section{Behaviour Analytics}
The portal observes the keyboard events of the editor. It computes the typing speed in words per minute, the variance of the time between key presses, the share of deleting keys, the idle time, and large insertions of text that appear in an instant. The rules compare these values with limits: a speed above 140 words per minute, a long idle period followed by a burst of typing, a variance below 12 ms, or an insertion of 40 characters or more within 50 ms. Each rule adds points to a suspicion score between 0 and 100, which falls slowly while the student types normally. Scores below 25 are shown as normal, from 25 to 59 as unusual, and 60 or more as high risk. The values and the current code are sent to the server every five seconds, and at once when a rule fires. Replacing the text of the editor by the program itself, for example when changing the question, is not counted as typing.

\section{Admin Server and Web Dashboard}
The Admin Server is an Electron application that starts an Express server and a Socket.IO server in the same process. On every start it generates a new six-digit password for the administrator. The dashboard in the browser asks for this password, receives a session and a signed token, and uses the token for every command sent through the socket.

The dashboard has seven pages. The live monitor shows the examination settings and all connected students. The analysis page shows the typing metrics and the current code of every student. The webcam alerts page lists the violations with their snapshots. The students page registers students, imports a CSV file and assigns questions. The questions page adds, edits and previews questions. The log page shows the events recorded by the server, and the database page downloads a backup of the database. From these pages the invigilator can warn, lock or unlock a student, remove the binding of a computer, force a submission or cancel it, send an announcement to everyone, and open the submitted programs and run them. The screenshots are in Appendix~A.

\section{Submission and Review}
The button Save sends the code of the open question to the server, where it is stored in the database and in a file. At the end, either by the student or when the time is over or on a command of the invigilator, the portal sends all code buffers and then uploads a compressed copy of the workspace with an HTTP request. The request carries a token that the server created at login, so only the logged-in student can upload for that roll number. The server writes the files into a folder of the student, keeps only the plain file names from the archive and ignores anything else, so an archive cannot place files outside the folder. After the upload the student is marked as submitted.

If the network is lost during the examination, the portal keeps the examination on the screen, shows a banner, reconnects by itself and logs the student in again without any action. The code is also kept on the computer under the roll number, so that a restart does not lose it.

\section{Network Address Discovery and Firewall}
On a laptop that has virtualisation software installed there are several network adapters, and the first one in the list is often a virtual adapter whose address cannot be reached by other computers. The Admin Server therefore classifies every adapter. It recognises virtual adapters by the first bytes of their hardware address and by their names, ignores addresses that Windows gives when no network exists, and ranks the rest: the hotspot of the laptop first, then wired and then wireless networks. All usable addresses are shown in the application and are refreshed every three seconds, so a hotspot that is switched on later appears at once. On the student side the portal asks the operating system which adapter would be used to reach the server and reports that address.

Windows blocks incoming connections by default. The installer of the Admin Server runs with administrator rights and therefore creates two firewall rules, one for the program and one for port 3000, valid on all network types, and removes them when the program is uninstalled.

\section{Packaging and Installation}
Both applications are packaged with electron-builder into a setup program for all users of the computer. The setup shows a side panel with the university seal, installs the program to Program Files, creates the shortcuts and an entry for uninstalling, and keeps the licence and the database when the program is removed. The Student Portal setup contains the embedded Python and the GCC compiler. Tools that the examination never uses, such as the debugger and the build system that come with the compiler package, are left out, which reduced the compiler folder from 868 MB to 508 MB. With compression the student setup is 191 MB and the admin setup is 86 MB.

\section{Observations and Limitations}
The camera proctor depends on the light and on the position of the camera. A face that is very small in the picture gives an unreliable iris position, so the iris is ignored when the face is narrower than one tenth of the picture and only the head direction is used. The thresholds of 30 degrees and of 2, 3 and 8 seconds were chosen from the geometry of a laboratory seat and are not final; they should be tuned with real candidates before the system is used for a formal examination.

The scan of the program text before running is a text pattern check. It stops direct calls, but a determined candidate may find a way around it, so the examination still relies on the lock of the computer and on the invigilator. The examination password of a student is stored as plain text in the database of the administrator, as the invigilator has to be able to read it out; the database file therefore has to be protected. The system was tested with one student client at a time and with simulated clients; a load test with a full laboratory remains to be done.

\chapter{Conclusion and Future Work}

\section{Conclusion}
This project produced an examination system for programming tests in a computer laboratory. It combines a locked student application, an integrated code runner with Python, C and C++, an administrator application with a live dashboard, and an on-device camera proctor, and it works on a local network without the internet. The proctor estimates head direction and iris position from face landmarks, calibrates itself for every student and reports violations with a snapshot, and no video is sent from the student's computer. The system is delivered as two installers with the compilers included. The tests show that the server, the code runner and the decision logic of the proctor behave as intended.

\section{Future Work}
The first step is to tune the thresholds of the proctor with recordings of real candidates in different light and seating, and to measure how often it gives false alarms. The system should then be tried with a complete laboratory to measure the load on the server and the network. Further work can add an automatic comparison of the output of a program with the test cases of the question and a similarity check of submitted programs, stronger isolation of the candidate's programs, for example with a restricted account or a container, and storing the examination passwords in a hashed form with a separate way to hand them to the candidates.
