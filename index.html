Paper-based examinations cannot test this, and unsupervised computer-based tests make it easy to look up answers, to copy code from a neighbour, to bring prepared code on a pen drive, or to ask another person for help. In a university laboratory the invigilator can see the room, but cannot see what is on thirty screens at the same time. A computer-based examination for programming therefore has to do three things together. It has to restrict what the candidate's computer can do during the examination, it has to give the candidate a working programming environment, and it has to give the invigilator a live view of what every candidate is doing. This project builds such a system for the computer laboratories of the Interdisciplinary Centre for Artificial Intelligence. \section{Existing Systems and Their Limitations} General-purpose quiz and coding platforms run in a web browser, need a stable internet connection and cannot stop the candidate from switching to another window. Browser lockdown tools restrict the computer but do not provide a place to compile and run programs, and cloud proctoring services upload the candidate's video to a remote server. A laboratory needs a single system that works on its own network, locks the computer, runs the candidate's code locally and monitors the candidate without sending video elsewhere. \section{Objectives} The objectives of the project are: \begin{enumerate} \item To restrict the computer of the student to the examination application in full-screen mode, with other applications, system shortcuts and removable drives blocked until the examination ends. \item To provide inside the same application an environment in which Python, C and C++ programs can be written, compiled and run, without installing any software on the computer beforehand. \item To let the administrator register students, create and assign questions, start or schedule the examination and watch the live status of every student from one dashboard. \item To detect looking aside, looking down, absence of the candidate and a covered or disconnected camera, using only processing on the candidate's computer, and to report each case to the administrator with a snapshot. \item To bind the software to authorised computers with a licence token, and to bind every student to one computer. \item To work completely on a local network, without an internet connection. \item To package both applications as Windows installers that can be deployed on laboratory computers. \end{enumerate} \section{Organisation of the Report} Chapter~2 describes the existing systems and the literature. They are built for a large number of candidates in different places and need a stable internet connection. The candidate works inside an ordinary browser, so the computer is not restricted: other windows, search engines and messaging applications stay available, and the platform has no view of the room. After the test, a similarity checker such as MOSS can compare the submitted programs. It is based on document fingerprinting by winnowing~\cite{winnowing} and finds copied code only after the examination, when the damage is already done. \section{Learning-Management Systems and Programming Plug-ins} Learning-management systems such as Moodle provide quizzes with timers and question banks. Plug-ins such as CodeRunner and the Virtual Programming Lab add programming questions that are evaluated on the server of the institution. This suits a laboratory network, because the server is local, but the examination still runs in a normal browser. The browser can be left at any moment, there is no built-in camera supervision, and the programs of all candidates are executed on the one server, which has to be secured against hostile code. \section{Lockdown Browsers and Kiosk Applications} Safe Exam Browser~\cite{seb} opens an examination web page in a locked browser window, blocks other applications and disables shortcuts. Commercial lockdown browsers for learning-management systems work in the same way. They protect web-based quizzes well, but they offer no compiler, so a program cannot be compiled and run inside them, and they do not watch the candidate. Building a locked application with a desktop framework such as Electron~\cite{electron} makes it possible to combine the lock with a local code runner, because the application can reach the operating system through a controlled bridge. \section{Remote Proctoring Services} Cloud proctoring services use the webcam and the microphone of the candidate, record the session and let a person or an automatic system review it afterwards~\cite{atoum}. They are made for candidates at home. The video of the candidate is uploaded to a server of the provider, which raises questions of privacy and needs a good network connection. In a laboratory the invigilator is in the room, so what is needed is not a recording but a prompt, private warning that something is wrong. \section{Face, Head and Gaze Analysis} Camera-based proctoring estimates whether the candidate is looking at the screen. The two common signals are the direction of the head and the direction of the eyes; surveys of the two topics are given in~\cite{murphy,hansen}. Learning-based methods estimate the gaze from an image of the eye~\cite{mpiigaze}, but they need a trained model for gaze and are sensitive to the conditions of the camera. MediaPipe~\cite{mediapipe} provides a framework for running perception models on the device. Its face mesh model estimates 468 three-dimensional landmarks of the face in real time on ordinary hardware~\cite{kartynnik}, and a later model adds the tracking of the iris~\cite{iris}. The Face Landmarker task~\cite{landmarker} combines these outputs with blendshape scores that describe, for example, the eyelids and the direction of the eyes. These values are enough to compute head yaw and pitch and an iris position inside the eye without training a new model, which is the basis of the proctor in this project. \section{Behaviour-Based Detection} Besides the picture of the candidate, the way of working can be observed. Typing rhythm has been studied for a long time as a property of a person~\cite{keystroke}, and sudden insertion of a large block of text, a very high typing speed or long idle periods followed by a burst are signs that code may have been pasted or typed by someone else. Such signs do not prove misuse, so the system in this project turns them into a score that the invigilator can read, and the decision stays with the invigilator. \section{Comparison with the Proposed System} Table~\ref{tab:compare} compares the approaches that were studied with the system developed here. \begin{table}[H] \centering \caption{Comparison of examination approaches}\label{tab:compare} \footnotesize \begin{tabularx}{\textwidth}{@{}Y c c c c@{}} \toprule \textbf{Approach} & \textbf{Locks PC} & \textbf{Runs code locally} & \textbf{Camera proctoring} & \textbf{Works on LAN only}\\ \midrule Online judges & No & No & No & No\\ Moodle quiz with plug-ins & No & No & No & Yes\\ Lockdown browser & Yes & No & No & Partly\\ Cloud proctoring service & Partly & No & Yes & No\\ \textbf{This project} & \textbf{Yes} & \textbf{Yes} & \textbf{Yes} & \textbf{Yes}\\ \bottomrule \end{tabularx} \end{table} None of the systems studied combines a locked computer, local compilation of programs, camera proctoring that is done on the computer of the candidate, an analysis of the typing behaviour, and operation on a local network without the internet. The present work takes the lock from kiosk applications, the local server from learning-management systems, and the face landmarks from the research on face analysis, and joins them in one system. %% ---------------------------------------------------------------------- \chapter{System Analysis} %% ---------------------------------------------------------------------- \section{Functional Requirements} The functions that the system must provide are listed in Table~\ref{tab:fr}. \begin{table}[H] \centering \caption{Functional requirements}\label{tab:fr} \footnotesize \begin{tabularx}{\textwidth}{@{}c Y@{}} \toprule \textbf{No.} & \textbf{Requirement}\\ \midrule FR1 & The administrator registers students one by one or from a CSV file, creates questions and assigns questions to students.\\ FR2 & The administrator starts the examination at once or at a scheduled time, and the timer of every student follows the examination duration.\\ FR3 & A student logs in with a roll number and a password. ---------------------------------------------------------------------- \section{System Architecture} The system follows a client--server design on a single local network, as shown in Figure~\ref{fig:arch}. The administrator creates a licence token file with the Admin Server and copies it to a USB drive. When the drive is inserted the portal finds the token, decrypts it with AES-256-CBC and, if it is valid, writes a machine lock file. The lock stores the hardware identifier of the computer, which is read from the system, encrypted with AES-256-CBC, and is checked at every start. Copying the installed program to another computer therefore does not work. A second binding is made at the server. The first time a student logs in, the address of the computer is stored with the roll number. A login from another address is rejected until the administrator removes the binding, which is needed when a computer fails and the student has to move to another one. \section{Examination Lockdown} The main window is created in full-screen kiosk mode, always on top and without a frame. The renderer runs with context isolation and the Chromium sandbox switched on and with Node.js disabled, and the page carries a content security policy that allows nothing from the network. The only permission granted to the page is the camera. Shortcuts such as Alt+Tab, Alt+F4, the Windows key, the function keys and the developer tool shortcuts are registered and swallowed by the application. A small helper program installs a low-level keyboard hook for the keys that Windows does not hand to an application. Whenever the window loses focus, it is brought back and the event is counted and sent to the server. A second helper listens to the Windows management events for a new removable drive. If a drive is inserted during the examination the server locks that student and shows an alarm on the dashboard. The invigilator can leave the locked application with a secret key combination. \section{Code Execution Module} Every student has a workspace folder named after the roll number. The program that is open in the editor is written to a file in this folder, so helper files and several source files can be used together. For C and C++ the file is compiled with the bundled GCC 16.1.0 using static linking, and the result is started as a separate process. Python programs are started with the embedded interpreter in unbuffered mode, so that output appears while the program is still running. The standard input of the process is connected to the terminal of the portal, which makes interactive programs possible. A process is stopped after 120 seconds or after 300 KB of output. Before a program is started, its text is scanned for calls that give access to the operating system, for example the \texttt{os} and \texttt{subprocess} modules in Python and \texttt{system()} in C. File names that arrive from the page are checked against a strict pattern so that a name cannot point outside the workspace. The scan is a first barrier and not a complete sandbox. It is mentioned again among the limitations in Chapter~6. \section{AI Proctoring Module} \subsection{Frame Capture and Landmark Detection} The camera is opened at 640$\times$480 and about ten frames per second are analysed. The MediaPipe Face Landmarker returns 478 landmarks for the face, of which ten belong to the irises, and a set of blendshape scores. The model file and the WebAssembly runtime are part of the installer, so nothing is downloaded. The detector uses the graphics processor when it is available and the processor otherwise. \subsection{Head Direction and Eye Direction} The head yaw $\psi$ is estimated from the position of the nose tip $x_n$ between the two edges of the face $x_L$ and $x_R$. Because the nose projects about half a face width in front of the face contour, the offset of the nose is $0.5\tan\psi$, which gives \begin{equation} \psi = \arctan\!\left(\frac{2\,\bigl(x_n-\tfrac{x_L+x_R}{2}\bigr)}{x_R-x_L}\right). \end{equation} For each eye the position of the iris centre $x_i$ between the outer corner $x_o$ and the inner corner $x_c$ of the eye is \begin{equation} r = \frac{x_i-x_o}{x_c-x_o}, \end{equation} and $\bar r$ is the mean of both eyes. The pitch ratio $\rho$ compares the vertical position of the nose tip $y_n$ with the brow $y_b$ and the chin $y_c$: \begin{equation} \rho = \frac{y_n-y_b}{y_c-y_b}. \end{equation} A student who looks at the screen has some values $\psi_0$, $\bar r_0$ and $\rho_0$ that depend on the seat and on the position of the camera. The direction of gaze is therefore measured relative to these values: \begin{equation} \theta = (\psi-\psi_0) + 150\,(\bar r-\bar r_0). \end{equation} The factor 150 converts the shift of the iris inside the eye into degrees and was chosen from the geometry of the eyeball. The student is treated as looking aside when $|\theta|$ exceeds $30^\circ$. Looking down is detected when $\rho-\rho_0$ exceeds 0.10 or when the blendshape for eyes looking down rises by more than 0.35 above its calibrated value. All angles are signed so that left and right refer to the student's own left and right. \subsection{Calibration and Violation Rules} When the examination starts, the portal asks the student to look at the screen for about two seconds. The median of 15 suitable frames gives $\psi_0$, $\bar r_0$ and $\rho_0$. Frames in which the head is already turned or the eyes are closed are ignored. If the student does not look at the screen, neutral values are used. Values of a single frame are noisy, so they are smoothed and a violation needs a condition to hold for some time. It computes the typing speed in words per minute, the variance of the time between key presses, the share of deleting keys, the idle time, and large insertions of text that appear in an instant. The rules compare these values with limits: a speed above 140 words per minute, a long idle period followed by a burst of typing, a variance below 12 ms, or an insertion of 40 characters or more within 50 ms. Each rule adds points to a suspicion score between 0 and 100, which falls slowly while the student types normally. Scores below 25 are shown as normal, from 25 to 59 as unusual, and 60 or more as high risk. The values and the current code are sent to the server every five seconds, and at once when a rule fires. All usable addresses are shown in the application and are refreshed every three seconds, so a hotspot that is switched on later appears at once. On the student side the portal asks the operating system which adapter would be used to reach the server and reports that address. Windows blocks incoming connections by default. The examination password of a student is stored as plain text in the database of the administrator, as the invigilator has to be able to read it out; the database file therefore has to be protected. The system was tested with one student client at a time and with simulated clients; a load test with a full laboratory remains to be done. %% ---------------------------------------------------------------------- \chapter{Conclusion and Future Work} %% ---------------------------------------------------------------------- \section{Conclusion} This project produced an examination system for programming tests in a computer laboratory. It combines a locked student application, an integrated code runner with Python, C and C++, an administrator application with a live dashboard, and an on-device camera proctor, and it works on a local network without the internet. The proctor estimates head direction and iris position from face landmarks, calibrates itself for every student and reports violations with a snapshot, and no video is sent from the student's computer. The system is delivered as two installers with the compilers included. The tests show that the server, the code runner and the decision logic of the proctor behave as intended. \section{Future Work} The first step is to tune the thresholds of the proctor with recordings of real candidates in different light and seating, and to measure how often it gives false alarms. The system should then be tried with a complete laboratory to measure the load on the server and the network. Further work can add an automatic comparison of the output of a program with the test cases of the question and a similarity check of submitted programs, stronger isolation of the candidate's programs, for example with a restricted account or a container, and storing the examination passwords in a hashed form with a separate way to hand them to the candidates. %% ---------------------------------------------------------------------- %% REFERENCES %% ---------------------------------------------------------------------- \clearpage \renewcommand{\bibname}{References} \addcontentsline{toc}{chapter}{References} \begin{thebibliography}{9} \singlespacing \bibitem{kurnia} A.
